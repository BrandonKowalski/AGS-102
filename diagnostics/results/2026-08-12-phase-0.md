# Phase 0 results

Recorded against unmodified BaseOS 1.1.0 on an **RG SP**, serial
`ac001089c8958701d12`, over adb on 2026-08-12. The card carries `slot`, not
NextUI, so every "how the device behaves" answer below is the real target
configuration rather than an approximation of it.

Note on this image: its `/etc/init.d/rcS` has **no `os_sleep` line**. The card
was built from BaseOS 1.1.0 (Jul 28); the Super Standby commit `e53276a`
landed Jul 29. So nothing here was measured with Super Standby enabled, and
every claim about Super Standby remains untested on hardware.

## T0 — RG SP cold boot

**PASS.** BaseOS 1.1.0, kernel `4.9.170 #2 SMP PREEMPT Wed Jun 24 2026`,
aarch64. All five `/run/boot-*` markers present, adb up, `slot` running from
the card. As far as is known this is the first RG SP boot with BaseOS by
anyone — upstream's README still lists the target as unconfirmed.

## T1 — enumeration

- **Does the cmdline set `console=`?** Yes — `console=ttyS0,115200`, plus
  `earlyprintk=sunxi-uart,0x05000000` and `loglevel=4`. `quiet splash` is also
  present, so rung A's win comes from removing the console and earlyprintk, not
  from adding `quiet`.
- **Anything on the AXP2202 that could force the PMIC off?** **No.** The driver
  publishes a large vendor-specific set — `hallkey`, `os_sleep`, `boot_mode`,
  `work_led`, `workload_sleep`, `lowpwr_led`, `nds_pwrkey`, `nds_esckey`,
  `moto`, `spk_state`, `openbor_volume`, `brightness`, `display_id` — but
  nothing that names a shutdown or power-cut. This is the design spec §11 risk
  scenario: there may be no userspace route to a real power off.
- **Battery:** `axp2202-battery`, `charge_full` = `energy_full_design` =
  **3500000 µAh (3500 mAh)**. This is the `--nominal-uah` value for
  `ags-analyse.py`. `charge_counter` is live and tracks `capacity` correctly.
- **Is `wakealarm` present?** **Yes** — `/sys/class/rtc/rtc0/wakealarm` exists,
  alongside a second RTC (`rtc1`) that has no `wakealarm`. Primitive 4 of the
  design spec §5.2 is available.
- `os_sleep` exists but reads **empty** in every state; it appears write-only.

## T2 — lid events

**The lid is not an input device on this board.** Every node reports `sw = 0`:

```
event0 / input0  axp2202-pek        ev=100003  sw=0
event1 / input1  ANBERNIC-keys      ev=20000b  sw=0
event2 / input2  dierct-keys-polled ev=3       sw=0
```

There is no `SW_LID` anywhere, so `slot`'s `pick_devices` — which requires
`SW_LID` in a node's `sw` bitmap — cannot ever see the lid. This is a complete
explanation for the lid doing nothing, and it is a property of the hardware, not
a `slot` bug.

**The lid is `/sys/class/power_supply/axp2202-battery/hallkey`**, measured
directly:

| lid | `hallkey` |
|---|---|
| open | `1` |
| closed | `0` |

Confirmed by an edge on IRQ 120 and by `dmesg`: `hall_switch_isr` →
`hall_press_work_func: state=0` on close, `hall_release_work_func` on open.

`slot` must poll `hallkey`. Its current `EV_SW`/`SW_LID` decoding is dead code
on this hardware.

## T4 — is "sleep" actually sleep

**Suspend-to-RAM is real on this board and it resumes.** Measured:

```
PM: suspend entry 2026-08-12 15:50:27
PM: Suspending system (mem)
PM: suspend of devices complete after 943.330 msecs
Disabling non-boot CPUs ...
Enabling non-boot CPUs ...
PM: suspend exit 2026-08-12 15:50:45
```

`Suspending system (mem)` with non-boot CPUs powering down is genuine STR, and
uptime continued across it (195.06 → 221.06) rather than resetting.

**Standby current: not yet measured** — the device was charging throughout.
This is the other half of the overnight run.

Super Standby (`os_sleep` = 16): **never applied on this image** — see the note
at the top. Untested.

## T5 — lid as a wake source

**The hall switch does not wake the device from `mem`.**

It is wired as a wake IRQ — `/proc/interrupts` line 120 is
`sunxi_pio_edge 103 Edge  hall switch`, and dmesg records
`axp20x_pek_probe: 907 wakup_irq=120`, so the vendor registered it as the
power-key driver's wakeup source. Despite that, opening the lid from a `mem`
suspend did nothing; POWER was required.

There are no `/sys/class/input/*/device/power/wakeup` files at all, so the
standard "enable a wakeup source from userspace" route does not exist here. If
lid-open resume is wanted, the device tree is the remaining lever — as the
design spec anticipated.

### Anomaly: suspending with the lid closed is a one-way trip

| run | `os_sleep` | lid at suspend | outcome |
|---|---|---|---|
| 1 | untouched | **closed** | POWER produced a **cold boot** (uptime reset, bootlogo) |
| 2 | written `0` | open | **resumed**, adb back in ~4 s |
| 3 | untouched | open | **resumed**, but the USB gadget did not come back |

Runs 1 and 3 had identical PMIC configuration, so `os_sleep` is not the
variable — **the closed lid is**. Suspending with the lid shut appears to
enter a state only a cold boot exits. This needs at least one clean repeat of
each condition before it is treated as established, and it is squarely a
Phase 4 concern.

Two further observations, both consistent across every run:

- **POWER always took two presses** to bring the device back. The first press
  is plausibly consumed as the wake event itself, with only the second reaching
  userspace. If so it is a `slot` input concern, not a kernel fault.
- **adb does not reliably survive a suspend/resume cycle** (it returned after
  run 2, not after run 3), matching BaseOS's documented note that the sunxi
  manager clears the UDC when VBUS drops. A force-off and power-on with the
  cable connected restores it.

## T6 — U-Boot

`bootdelay=0`, confirmed. The environment on p3 stores the cmdline as a
template, so the boot-time work is a change to three *values*, not a rewrite:

```
setargs_mmc=setenv bootargs earlyprintk=${earlyprintk} initcall_debug=${initcall_debug} \
  console=${console} loglevel=${loglevel} root=${mmc_root} rootwait quiet splash \
  init=${init} partitions=${partitions} cma=${cma} snum=${snum} ... gpt=1
```

`bootcmd=run setargs_nand boot_normal` is what `strings` recovered, yet the live
cmdline carries `root=/dev/mmcblk0p5` and `rootwait quiet splash`, which appear
only in `setargs_mmc`. Either a second environment copy is authoritative or
U-Boot selects by boot medium. **Unresolved**, and worth settling before rung E
touches anything.

## Boot timing — first RG SP measurement

From `/run/boot-*` on a cold boot, seconds since kernel start:

| marker | RG SP | RG40XXV reference |
|---|---|---|
| `rcS-start` | 1.97 | 2.04 |
| `rcS-done` | 3.09 | 2.59 |
| `frontend-exec` | **3.10** | 2.96 |
| `dev-done` | 3.14 | — |
| `adb-gadget-done` | 3.44 | — |

`rcS` costs **1.12 s** on the RG SP against 0.55 s on the RG40XXV — twice as
long, and the largest single software target after the pre-`rcS` kernel time.
This supersedes the RG40XXV-derived 3.00 s ceiling in `validate-on-device.sh`,
which means nothing on this device.

## `slot` on the RG SP

Runs, and finds everything it needs:

```
slot: backlight dispdbg (0 to 255), battery axp2202-battery, rtc0
slot: audio plug:default at 32768 Hz
slot: input /dev/input/event0 (axp2202-pek)
slot: input /dev/input/event1 (ANBERNIC-keys)
slot: input /dev/input/event2 (dierct-keys-polled)
```

The `dispdbg` backlight fallback is the one in use, confirming the `debugfs`
mount is load-bearing. No lid among the inputs, per T2.

**The path this device actually takes to "off"**, from
`crates/slot/src/frontend.rs:21,70`: `Power::new(platform, SleepDepth::Doze,
DOZE_TIMEOUT)` with `DOZE_TIMEOUT = 300s`. Tapping POWER runs `doze()` — panel
off, **main loop still running mGBA at full speed** — for five minutes, then
sets `powering_off`, which calls `sync` + `poweroff`. No suspend is involved at
any point. Five minutes at full draw is on the order of 10–25 mAh and cannot by
itself flatten a 3500 mAh cell, so the `poweroff` at the end of it remains the
prime suspect for the overnight death.
