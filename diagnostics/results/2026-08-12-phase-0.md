# Phase 0 results

Recorded against unmodified BaseOS 1.1.0 on an **RG SP**, serial
`ac001089c8958701d12`, over adb on 2026-08-12. The card carries `slot`, not
NextUI, so every "how the device behaves" answer below is the real target
configuration rather than an approximation of it.

Note on this image: its `/etc/init.d/rcS` has **no `os_sleep` line**. The card
was built from BaseOS 1.1.0 (Jul 28); the Super Standby commit `e53276a`
landed Jul 29. So nothing here was measured with Super Standby enabled, and
every claim about Super Standby remains untested on hardware.

| Test | Device | Answer | Blocks |
|---|---|---|---|
| T0 does BaseOS boot on an RG SP | RG SP | **PASS** | the whole project |
| T1 what the board publishes | RG SP | done | the poweroff primitive |
| T2 how the lid reports itself | RG SP | done — not evdev | slot's input decoding |
| T3 is "off" actually off | RG SP | **works unplugged; 400-700 mA if VBUS present** | the power design |
| T4 is "sleep" actually sleep | RG SP | 141 mA without SS; **< 45 mA with `os_sleep=16`** | the lid design |
| T5 can the lid wake from mem | RG SP | **no** | whether the DTB gets patched |
| T6 what U-Boot does before the kernel | RG SP | done | boot-time rung E |

## T0 — RG SP cold boot

**PASS.** BaseOS 1.1.0, kernel `4.9.170 #2 SMP PREEMPT Wed Jun 24 2026`,
aarch64. All five `/run/boot-*` markers present, adb up, `slot` running from
the card. As far as is known this is the first RG SP boot with BaseOS by
anyone — upstream's README still lists the target as unconfirmed.

## T1 — enumeration

- **Does the cmdline set `console=`?** Yes — `console=ttyS0,115200`, plus
  `earlyprintk=sunxi-uart,0x05000000` and `loglevel=4`. `quiet splash` is also
  present, so rung A's win comes from removing the console and earlyprintk, not
  from adding `quiet`.
- **Anything on the AXP2202 that could force the PMIC off?** **No.** The driver
  publishes a large vendor-specific set — `hallkey`, `os_sleep`, `boot_mode`,
  `work_led`, `workload_sleep`, `lowpwr_led`, `nds_pwrkey`, `nds_esckey`,
  `moto`, `spk_state`, `openbor_volume`, `brightness`, `display_id` — but
  nothing that names a shutdown or power-cut. This is the design spec §11 risk
  scenario: there may be no userspace route to a real power off.
- **Battery:** `axp2202-battery`, `charge_full` = `energy_full_design` =
  **3500000 µAh (3500 mAh)**. This is the `--nominal-uah` value for
  `ags-analyse.py`. `charge_counter` is live and tracks `capacity` correctly.
- **Is `wakealarm` present?** **Yes** — `/sys/class/rtc/rtc0/wakealarm` exists,
  alongside a second RTC (`rtc1`) that has no `wakealarm`. Primitive 4 of the
  design spec §5.2 is available.
- `os_sleep` exists but reads **empty** in every state; it appears write-only.

## T2 — lid events

**The lid is not an input device on this board.** Every node reports `sw = 0`:

```
event0 / input0  axp2202-pek        ev=100003  sw=0
event1 / input1  ANBERNIC-keys      ev=20000b  sw=0
event2 / input2  dierct-keys-polled ev=3       sw=0
```

There is no `SW_LID` anywhere, so `slot`'s `pick_devices` — which requires
`SW_LID` in a node's `sw` bitmap — cannot ever see the lid. This is a complete
explanation for the lid doing nothing, and it is a property of the hardware, not
a `slot` bug.

**The lid is `/sys/class/power_supply/axp2202-battery/hallkey`**, measured
directly:

| lid | `hallkey` |
|---|---|
| open | `1` |
| closed | `0` |

Confirmed by an edge on IRQ 120 and by `dmesg`: `hall_switch_isr` →
`hall_press_work_func: state=0` on close, `hall_release_work_func` on open.

`slot` must poll `hallkey`. Its current `EV_SW`/`SW_LID` decoding is dead code
on this hardware.

## T3 — is "off" actually off

**No. `poweroff` does not cut power.** Measured on the RG SP, 2026-08-12,
unplugged for the whole window:

```
before   3500000 uAh  100%  Full        epoch 1786552429
after    3255000 uAh   93%  Charging    epoch 1786553688
elapsed  1259 s (21.0 min)
drawn    245 mAh  ->  700.6 mA average
```

Method: stamp the gauge to the card, run `poweroff` (the same software path
`slot` reaches at the end of its doze), unplug the cable the moment the screen
goes dark, leave it untouched, then plug in and hold POWER to boot. The device
did not respond to short POWER presses during the window, consistent with being
either off or wedged.

**At 700 mA a 3500 mAh cell is flat in five hours; at 430 mA, in eight.** Either
figure flattens the battery overnight, which is the reported fault.

### How much to trust 700 mA

Not fully. Two corrections, both pushing the same way:

- **`charge_counter` is derived, not accumulated.** On this board it is exactly
  `capacity` x `charge_full`: 2870000/3500000 = 0.82 when capacity read 82,
  2975000/3500000 = 0.85 when it read 85, 3255000/3500000 = 0.93 when it read
  93. Its true resolution is therefore 1% = 35 mAh, and it carries every
  artifact of the fuel gauge's own SoC estimate. **BaseOS's `docs/05` treats
  this attribute as a hardware coulomb counter and concluded real deep sleep
  from it "not moving" over 35 minutes — that inference does not hold on this
  hardware.**
- **The run started from `Full`.** A freshly-full cell reports a fast initial
  percentage drop that is surface charge rather than real discharge, so the
  first 2-3 points are inflated.

Discounting generously still leaves **400-500 mA**. The conclusion — the SoC is
still running with the rails up — is not in doubt; the exact figure is.

**A cleaner repeat** would start from ~80% rather than Full and run 60+ minutes,
which removes the surface-charge artifact and puts several honest percent
between the endpoints.

### Consequence for the design

Design spec section 11's third risk has fired. `poweroff` reaches
`reboot(RB_POWER_OFF)` and the machine does not power down, and T1 found **no
AXP2202 attribute able to force the PMIC off**. The only proven route to a real
power off on this board is the PMIC's own hardware long-press
(`pmu_powkey_off_time = 6000`, `pmu_powkey_off_func = 0`), which is not
reachable from software.

That makes the sleep-to-off escalation in section 5.3 unimplementable as
written, and it is now a product decision rather than a hypothetical one.

## T4 — is "sleep" actually sleep

**Suspend-to-RAM is real on this board and it resumes.** Measured:

```
PM: suspend entry 2026-08-12 15:50:27
PM: Suspending system (mem)
PM: suspend of devices complete after 943.330 msecs
Disabling non-boot CPUs ...
Enabling non-boot CPUs ...
PM: suspend exit 2026-08-12 15:50:45
```

`Suspending system (mem)` with non-boot CPUs powering down is genuine STR, and
uptime continued across it (195.06 → 221.06) rather than resetting.

**Standby current: 141 mA. This is not deep sleep.** Measured on the RG SP,
unplugged, `os_sleep` never written:

```
before  counter=3255000  cap=93%  uptime=329.01   epoch=1786554000
after   counter=3150000  cap=90%  uptime=3001.36  epoch=1786556672  Discharging
        105 mAh over 2672 s  ->  141 mA average
```

uptime advanced 329 -> 3001 while the wall clock advanced by the same 2672 s,
which independently confirms a real suspend/resume (no cold boot) and shows
`/proc/uptime` counts suspended time on this kernel. Gauge resolution (1% =
35 mAh) puts the honest range at roughly **95-190 mA**, or about **25 hours of
standby**.

For comparison, `docs/05` records the RG40XXV's coulomb counter not moving at
all across a 35-minute suspend. The RG SP is nowhere near that.

### The state of play after T3 and T4

| path | draw | standby life |
|---|---|---|
| awake, `performance` governor at 1512 MHz | ~400-700 mA | ~5-8 h |
| software `poweroff` (PSCI SYSTEM_OFF -> BL31) | 400-700 mA | 5-8 h |
| `mem` suspend, no Super Standby | 141 mA | ~25 h |

Suspend is only 3-5x better than running. Real STR should be ~100x. **No path
reachable from software currently gives this board a good low-power state.**

### The untested lever

Super Standby (`os_sleep = 16`) was **never applied in any measurement here** —
this image predates it. BaseOS committed `e53276a` to add it for SP kernels the
day after this build was made, which suggests upstream hit the same wall.

Next test: write `16`, suspend, measure identically. If it reaches single-digit
mA the mechanism is found, and the remaining question is whether it still
resumes — `docs/05` claims Super Standby narrows the wake set, which would make
this a direct standby-versus-lid-wake tradeoff with numbers on both sides.

## T5 — lid as a wake source

**The hall switch does not wake the device from `mem`.**

It is wired as a wake IRQ — `/proc/interrupts` line 120 is
`sunxi_pio_edge 103 Edge  hall switch`, and dmesg records
`axp20x_pek_probe: 907 wakup_irq=120`, so the vendor registered it as the
power-key driver's wakeup source. Despite that, opening the lid from a `mem`
suspend did nothing; POWER was required.

There are no `/sys/class/input/*/device/power/wakeup` files at all, so the
standard "enable a wakeup source from userspace" route does not exist here. If
lid-open resume is wanted, the device tree is the remaining lever — as the
design spec anticipated.

### Anomaly: suspending with the lid closed is a one-way trip

| run | `os_sleep` | lid at suspend | outcome |
|---|---|---|---|
| 1 | untouched | **closed** | POWER produced a **cold boot** (uptime reset, bootlogo) |
| 2 | written `0` | open | **resumed**, adb back in ~4 s |
| 3 | untouched | open | **resumed**, but the USB gadget did not come back |

Runs 1 and 3 had identical PMIC configuration, so `os_sleep` is not the
variable — **the closed lid is**. Suspending with the lid shut appears to
enter a state only a cold boot exits. This needs at least one clean repeat of
each condition before it is treated as established, and it is squarely a
Phase 4 concern.

Two further observations, both consistent across every run:

- **POWER always took two presses** to bring the device back. The first press
  is plausibly consumed as the wake event itself, with only the second reaching
  userspace. If so it is a `slot` input concern, not a kernel fault.
- **adb does not reliably survive a suspend/resume cycle** (it returned after
  run 2, not after run 3), matching BaseOS's documented note that the sunxi
  manager clears the UDC when VBUS drops. A force-off and power-on with the
  cable connected restores it.

## T6 — U-Boot

`bootdelay=0`, confirmed. The environment on p3 stores the cmdline as a
template, so the boot-time work is a change to three *values*, not a rewrite:

```
setargs_mmc=setenv bootargs earlyprintk=${earlyprintk} initcall_debug=${initcall_debug} \
  console=${console} loglevel=${loglevel} root=${mmc_root} rootwait quiet splash \
  init=${init} partitions=${partitions} cma=${cma} snum=${snum} ... gpt=1
```

`bootcmd=run setargs_nand boot_normal` is what `strings` recovered, yet the live
cmdline carries `root=/dev/mmcblk0p5` and `rootwait quiet splash`, which appear
only in `setargs_mmc`. Either a second environment copy is authoritative or
U-Boot selects by boot medium. **Unresolved**, and worth settling before rung E
touches anything.

## Boot timing — first RG SP measurement

From `/run/boot-*` on a cold boot, seconds since kernel start:

| marker | RG SP | RG40XXV reference |
|---|---|---|
| `rcS-start` | 1.97 | 2.04 |
| `rcS-done` | 3.09 | 2.59 |
| `frontend-exec` | **3.10** | 2.96 |
| `dev-done` | 3.14 | — |
| `adb-gadget-done` | 3.44 | — |

`rcS` costs **1.12 s** on the RG SP against 0.55 s on the RG40XXV — twice as
long, and the largest single software target after the pre-`rcS` kernel time.
This supersedes the RG40XXV-derived 3.00 s ceiling in `validate-on-device.sh`,
which means nothing on this device.

## `slot` on the RG SP

Runs, and finds everything it needs:

```
slot: backlight dispdbg (0 to 255), battery axp2202-battery, rtc0
slot: audio plug:default at 32768 Hz
slot: input /dev/input/event0 (axp2202-pek)
slot: input /dev/input/event1 (ANBERNIC-keys)
slot: input /dev/input/event2 (dierct-keys-polled)
```

The `dispdbg` backlight fallback is the one in use, confirming the `debugfs`
mount is load-bearing. No lid among the inputs, per T2.

**The path this device actually takes to "off"**, from
`crates/slot/src/frontend.rs:21,70`: `Power::new(platform, SleepDepth::Doze,
DOZE_TIMEOUT)` with `DOZE_TIMEOUT = 300s`. Tapping POWER runs `doze()` — panel
off, **main loop still running mGBA at full speed** — for five minutes, then
sets `powering_off`, which calls `sync` + `poweroff`. No suspend is involved at
any point. Five minutes at full draw is on the order of 10–25 mAh and cannot by
itself flatten a 3500 mAh cell, so the `poweroff` at the end of it remains the
prime suspect for the overnight death.

## T4b — Super Standby (`os_sleep = 16`)

**Works. No measurable drain over 47 minutes, and it still resumes.**

```
before  counter=3115000  cap=89%  Discharging  usb=0  epoch=1786558405  uptime=3.22
after   counter=3115000  cap=89%                      epoch=1786561212  uptime=2810.43
        2807 s (46m47s) elapsed — counter and capacity both unchanged
```

```
[3.235] PM: suspend entry 2026-08-12 18:13:25
[5.420] PM: suspend exit  2026-08-12 19:00:12
```

printk time advanced 2.18 s across 46m47s of wall clock, and `/proc/uptime`
advanced by the full 2807 s — the same signature T4 showed, so this was a real
suspend for essentially the whole window.

**Bound, not a measurement:** the gauge moves in 1% steps (35 mAh), so anything
under 35 mAh in 47 minutes is invisible. That puts standby **below 45 mA** and
gives **more than 3 days**. The true figure could be anywhere from ~40 mA down
to microamps — at 5 mA it would be about a month. An overnight run is the only
way to turn this into a number.

**Resume is not broken by Super Standby.** `docs/05` warns that it narrows the
wake set; POWER and cable-plug both still woke the device. Whether the *lid* can
wake it under Super Standby is untested — T5 established the lid cannot wake it
without Super Standby, so there is no reason to expect this to help.

### Measured comparison

| path | draw | standby life |
|---|---|---|
| awake, `performance` at 1512 MHz | ~400-700 mA | ~5-8 h |
| software `poweroff` (PSCI -> BL31) | 400-700 mA | 5-8 h |
| `mem` suspend, no Super Standby | 141 mA | ~25 h |
| **`mem` suspend, `os_sleep = 16`** | **< 45 mA** | **> 3 days** |

**This board does have a working low-power state, and BaseOS's `e53276a` was
right to add it.** AGS-102 must write `os_sleep = 16` at boot. Note the caveat
carried from T4: WiFi was up during every one of these measurements, since
`rcS` brings `wlan0` up unconditionally — so even the 141 mA figure was not a
clean measurement of the sleep path itself.

### What this does to the design

"Off" should be **suspend with Super Standby**, not `poweroff`. It is reachable
from software, it resumes, and it is at worst 3 days of standby against 5-8
hours for a `poweroff` that does not power off. `slot` already save-states, so
resume is instant rather than a 3.1 s boot.

The PMIC's 6 s long-press remains the only candidate for a true power off and is
**still unmeasured** (T3b).

## Incident — the broken poweroff can latch the device unrecoverably

2026-08-12, RG SP, during Phase 0. Sequence:

1. POWER tapped; `slot` entered `Phase::Doze` (panel off, main loop still running).
2. Lid closed. Nothing handles the lid on this board, so this was cosmetic.
3. 300 s later `DOZE_TIMEOUT` fired, setting `powering_off`, which called
   `poweroff` — PSCI `SYSTEM_OFF` into BL31, the path measured at 400-700 mA in
   T3.
4. The device went black and **would not restart**.

Recovery attempts that **failed**:

- short POWER presses
- POWER held 8-10 s (past `pmu_powkey_off_time = 6000`, the PMIC's own hardware
  force-off, which had worked twice earlier the same day)
- the reset button
- charger connected, charge LED lit, repeated attempts

Recovery that **worked**: opening the case and disconnecting the battery.

The screen never showed U-Boot's bootlogo, which is drawn from p2 before any OS
code runs, so the SoC was not starting at all. USB never enumerated.

### Why this matters more than the drain

T3 established that `poweroff` leaves the SoC running at 400-700 mA. This
incident shows it can additionally leave the PMIC latched in a state that
survives its own hardware force-off. **An ordinary user hitting this has no
recovery short of disassembly.**

The trigger is not exotic. It is: tap POWER, walk away for five minutes. Every
user of this build can reach it, and `slot`'s `Action::PowerHold` reaches the
same `poweroff` by a second route.

### Consequence

`slot` must stop calling `poweroff` on every path. There is no working software
power off on this board (section T3, amendment 12.1), so:

- doze timeout -> `mem` suspend with `os_sleep = 16`
- power hold -> `mem` suspend
- a true power off is the PMIC's 6 s hold, in hardware, with `slot` not involved

**No further power experiments on hardware until that change lands.**

## T3 REVISED — `poweroff` works, but only with the cable out

T3 measured the wrong thing. It ran `poweroff` over adb, which requires the USB
cable, and the cable was unplugged only *after* the screen went dark. So it
measured **shutdown-while-charging**, not shutdown.

Re-run from the card harness, with VBUS already gone before `poweroff` was
issued (no adb involved at the moment it mattered):

```
before  counter=2730000  cap=78%  Discharging  usb=0  epoch=1786568285  waited=0s
after   counter=2730000  cap=78%                      epoch=1786570213  uptime=2.95
        1928 s (32.1 min) elapsed — counter and capacity both unchanged
```

`uptime=2.95` on the far side confirms a cold boot, so the device was genuinely
off rather than resumed.

### The actual rule

| condition | result |
|---|---|
| `poweroff` with VBUS present **when it runs** | 400-700 mA; can latch so hard that only a battery disconnect recovers it |
| `poweroff` with VBUS absent | **genuinely off, no measurable drain in 32 min** |
| `mem` suspend, `os_sleep = 16` | < 45 mA |
| `mem` suspend, no Super Standby | 141 mA |

The damage happens at the *instant of shutdown*, not during the off period: in
T3 the cable came out seconds later and the device still drained the whole
window. This is almost certainly what caused the unrecoverable latch recorded
above — that `poweroff` fired from `slot`'s doze timeout while plugged in.

Independently reported across the H700 community on hardware unrelated to ours
(knulli-cfw/distribution#472: *"if i shut my rg40xx down while plugged in, it
doesn't really shut down completely. but if it's charged, i unplug it and then
shut it down, it stays charged overnight"*), and #287 is the same fault on an
RG35XX SP by way of a charger-detection race.

### Consequence for the design

There **is** a working software power off, which restores the option amendment
12.1 had written off. The requirement is a precondition rather than a
mechanism:

- **Never call `poweroff` while VBUS is present.** Suspend instead, or wait for
  the cable to be removed.
- `slot` can read `/sys/class/power_supply/axp2202-usb/online` to decide, the
  same file the test harness used.
- This is a *safety* rule, not an optimisation: getting it wrong can require
  the user to open the case.

The `axp20x_device_shutdown` route and Shaun Inman's direct-i2c PMIC write
remain interesting as a way to make power off work unconditionally, but they
are no longer load-bearing for the design.
